# v1 实施方案：第二位工程师，第二个真实项目

## 1. 用户结果与范围

v0 已证明本人能在企业内网使用完整 OpenCode。本次只扩大到第二位真实工程师：给他/她一个已有授权项目、独立环境和清楚的交付方式，不让其配置 Agent 环境。

```text
管理员预配置 B 与项目 P2
      ↓
B 通过已沿用的企业登录进入 P2
      ↓
完整 OpenCode 阅读代码 → 修改 → 测试 → 检查 Diff
      ↓
下载源码/补丁 → 干净副本复现
      ↓
B 重进并继续第二轮；A 原有项目及历史不受影响
```

默认：两位真实身份、每人一个固定项目、一个已经支持的运行模板、现有批准模型。用户项目与业务源码可以不同；平台配置能力不向用户开放。禁止把首个示例复制为 P2 后声称验证了真实业务差异。

不做：多项目自助管理、任意仓库 URL 接入、自动 push/PR、任意端口发布、动态调度、通用插件平台、RAG、多个 Runtime、用户环境配置、本地连接器、新语言运行栈。需要这些能力的项目另列候选，本版不扩建。

## 2. 延续架构，只加已发生的差异

```text
管理员预配置（已有配置/脚本的小范围扩展）
                 │
         固定用户—项目—环境绑定
                 │
        已有企业入口 / platform / 受控路由
           ┌─────┴─────┐
       绑定 A         绑定 B
       环境 A         环境 B
       原生状态 A     原生状态 B
       项目 P1        项目 P2
       独立预览       独立预览
       独立预算       独立预算
```

复用现有 proxy、guard、模型网关、预览和导出，不改 OpenCode 循环。共享固定镜像和只读工具基线可以；可写工作目录、原生状态、作用域凭据和预算状态不能因复用而共享。完整 Agent 的操作确认、提问、停止、终端和继续工作能力必须保留。

### 最少的配置化

从已验收配置提取 A，不手填覆盖；新增 B 的身份、项目名称、仓库来源/固定基线、实例/目录、工作台与预览入口及受控凭据引用。示意见 [bindings.example.json](examples/bindings.example.json)。它不是现有生产接口，按实际代码做最小适配。

容器内路径继续统一 `/workspace/project`，不要为“去掉硬编码”让用户指定任意根目录。当前只有两个绑定时可仍用受控 JSON 与原子写文件；不要求 PostgreSQL、Redis 或调度队列。

管理员准备仓库使用受信任流程。工作容器不拿仓库写权限，不开放任意 clone URL。P2 必须在现有环境下完成一次基线构建/测试，并记录源提交、任务与测试标准。子模块/LFS等超出现有支持的情况在准备时明确拒绝或另选已支持项目，不悄悄交付不完整源码。

## 3. 入口与浏览器隔离

保留 A 当前入口和数据。旧单身份 IP 模式不要直接删限制后挂两个用户；在现有边界上添加 B 的独立入口。

优先使用企业 IT 可解析的内部主机名，工作台和生成应用采用不同主机名，不需要公网域名。也可使用企业已批准的独立地址方案，但必须通过相同 Cookie/Origin/存储隔离测试，不能仅靠端口。

来源 S6 说明 Cookie 不以端口隔离；独立主机名也不自动解决父域 Cookie 或跨源请求问题。平台认证 Cookie 限定 host-only，优先使用合适的 `__Host-` 属性组合；生成应用不得设置能影响平台身份的父域 Cookie，代理剥离或拒绝越界 Set-Cookie；验 Origin/Host、服务器端绑定和一次性票据；不能以 SameSite 代替身份校验。CSP、iframe 和 WebSocket 按现有代码实测，不删除防护来兼容 UI。

单一入口读取身份后只能得到该身份绑定；`userId`、`envId`、上游 URL、目录与原生 Session ID 等客户端数据不能改写路由。旧浏览器缓存、IndexedDB/localStorage、Service Worker、SSE、WS、预览票据和下载都属于隔离测试范围。

没有新增 DNS/证书条件就记录该具体增量阻塞；不要求用户重做已成功的 A 登录，也不把“无公网域名”当阻塞。不得关闭 TLS 校验或修改全局证书数据库。

## 4. 成果导出：先修实际缺陷，不造 Artifact 系统

本次源码复核范围是当前开发 HEAD，而非强制回退到审阅提交。先运行包内 [export-contract.mjs](tests/export-contract.mjs)。若已通过，保存结果，直接推进。

### 完整性

- 合法源码如 `src/db/query.ts`、`src/state/store.ts`、`src/runtime/worker.ts`、`src/credentials.ts` 不得因为名字而静默消失。
- 平台持有的 `.git`、原生状态、密钥及验证制品，按明确拥有的相对/绝对路径排除；不能把任意层级的 `runtime`、`state`、`vendor` 当作秘密目录。
- 依赖与构建产物按本次项目的已验证边界排除，既有上限可以保留；超限说明原因，不截断后仍宣称完整。
- `.npmrc`、`.netrc`、私钥、实际含凭据的环境文件不能进入 ZIP 或补丁。疑似敏感内容采用明确拦截/说明，不能靠“文件名里有 secret”替代全部判断。不要承诺检测所有形式的秘密。
- ZIP 和 patch 共用当前必要的排除判断，保留合理语义差异：ZIP 提供完整允许源码，patch 相对固定基线表达增加/修改/删除/二进制变化。

### 可解释与可复现

在已有导出返回/清单增加必要元数据，不要求新增数据库：项目/绑定、固定基线、捕获树或内容摘要、包括的文件、排除项及原因、生成时间；HTTP层/UI显示下载制品 SHA256。公开报告不要包含敏感字节，完整文件路径清单按所有权授权。

读实际下载文件验证，不仅验证内存函数返回。ZIP 在新目录解包并安装锁定依赖、测试/构建；patch 在同一固定基线的新副本 `git apply --check` 后应用并运行相同测试。记录制品摘要、基线、命令退出码和结果，不能拿之前某次通过的日志当这次成果的证明。

已有 `HEAD == baseline` 限制本版可继续保留。HEAD 不同要明确说明，不能自动 reset 用户文件或默默滚动基线。给 P2 任务明确采用未提交工作树交付，本版不扩展 Git 历史同步。

### 并发与可信快照

Agent idle 不保证 PTY 或后台进程没有改文件。导出前告知停止写任务；取得临时捕获后，从捕获数据生成清单、ZIP与patch并重新校验链接/文件类型。捕获期间检测到被保护源改变时应明确 `EXPORT_SOURCE_CHANGED`，不发一个声称已验证的包。

只靠开始/结束 hash 不能证明任意恶意并发时刻的全盘原子快照；本版不做这样的承诺。可交付承诺是“针对明确捕获的一份源码，在干净副本验证了该具体制品”。继续保持不执行项目 Git filter/hook、不修改用户索引的防护。安全边界失败时不返回部分下载。

## 5. 已验收数据保护与发布

新增 B 时，A 数据保持原地。记录 A 的会话标识、代表文件摘要、配置/证书指纹和预算，用于受影响面回归；若 A 正在正常工作，文件自然变化不等于回归，不冻结用户数小时以求所有字节不变。

先在不占用既有端口/名称/卷的开发或预发布资源验证，明确 namespace。生产发布只使用获准的本项目维护窗口。运行任务时拒绝破坏性重建；不停止同机模型或其他业务。

回退：撤回 B 的入口/配置和新制品，优先保留 A 原入口；保留 B 新数据以便恢复。不得为了版本回退自动还原旧数据备份覆盖本次新增会话。需要数据恢复的异常走独立、明确授权的恢复流程。

## 6. 任务与终点

执行 [TASKS.md](TASKS.md) 的四项有限工作，它们共同交付本次一条新路径，不是产品三阶段。验收按 [ACCEPTANCE.md](ACCEPTANCE.md)。v1 被两位工程师/负责人签收后停止扩建，下一需求从真实使用反馈产生。
