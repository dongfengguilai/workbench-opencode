# v1 增量验收契约

**v0 已由用户确认完成，不再判定 v0 是否可用。**下列项目属于 v1 新能力及其受影响面回归。必要时使用已有日志做基线，不要求用户重复此前完整验收。

任何 FAIL/NOT_RUN 都不自动变成 PASS；测试自通过与真实交付分开。结果记录到 [evidence/acceptance.json](evidence/acceptance.json)。最少证据：代码/制品标识、环境、测试命令或操作、时间、预期/实际结果及脱敏日志或文件摘要。

## 自动测试与真实验收的边界

[export-contract.mjs](tests/export-contract.mjs) 只覆盖 A07/A08 的一部分，外加索引/链接回归。绿色不表示 A02、A03、A09 或 A14 已通过。源码导出单测使用假密钥标记和临时 Git 仓库，不需要任何生产文件。

平台单元/契约测试可以用 fixture 身份。实际账号密码只在现有受控流程中使用，不放进测试仓库或对话。第二位真实身份的日志不足时保持未运行，不拿维护者账号换显示名称充数。

## P2 任务与独立验证

选定实际已有项目及基线后先定义修改结果和测试标准；保留基线测试结果。验证至少包含一次实现错误会失败的断言。若 Agent 修改测试，人工审查修改理由，独立保留关键验收断言。

记录第一次与第二次工作的 Session ID、内容差异及实际命令。复合命令退出 0 不自动表示前序命令通过；Playwright 的业务失败不因进程退出 0 而抹除。

生成应用只有受支持网页才要求对应浏览器验证；普通代码项目以代码/测试/成果闭环为准。但新增用户的预览隔离可用受控小型页面做安全验收，不扩展新的产品模板。

## 受影响回归如何控制范围

身份/代理变化：回归 A 登录和跨绑定拒绝、活跃流及退出；导出变化：回归 A 一次实际成果；部署变化：验证 A 数据原地保存与新资源回退。未修改的业务能力复用 v0 已接受结论，不重跑所有历史测试。

由于旧记录路径可能是维护者机器，允许以环境变量/CLI 参数指定测试目标；禁止为测试方便关闭正式 TLS、权限或实例隔离。

## 接收门槛

所有条目 PASS 且有对应新证据，v1 可以进入签收；完成用户确认后标记 ACCEPTED。附条件的真实外部阻塞可以分开记录，但不能边标 ACCEPTED 边保留核心路径 NOT_RUN。

无论 v1 新状态如何，v0 的历史用户确认不被撤销。新发现的已部署缺陷作为维护问题修复并回归，不改写过去的验收事实。
