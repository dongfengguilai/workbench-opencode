# 同一条主线的四个开发检查点

这些不是独立模块工程。当前用户路径不成立，就处理该路径的阻塞。修复已实现的部分只做回归，不重复编写。

## T0 — 找到一个值得改善的真实工作

读取实际工作副本和既有测试、项目、运行配置。继承 v2；记录候选来源与原生版本。先选择一个真实缺陷，记录用户期望、起始代码、基线验证和合法数据范围。

用**WorkBench 内实际 OpenCode**运行当前 v2 基线，记录真实消息和工具结果、人工帮助、耗时及请求量，找出一种明确的阻塞或低效。开发 Codex 可以布置测试、只读诊断和编写平台增量，不能替受测 Agent 修改答案后声称它成功。

冻结这个案例的验收与对照条件；设计后续 5—8 个案例及保留样本的范围。预算与指标在看候选结果前记录。无需先填满集合。

**交付**：首个真实案例记录、一项主要改善假设、最小改动范围和验收判据。

**止损**：没有真实案例则报告缺少哪种资料，完成必要的无外部依赖准备后停止扩建；基线已经足够好且无可解释缺口，则给出“暂不改动”结论，不造新功能。

## T1 — 在现有工作台打通第一个改善闭环

前后端同时围绕首个任务推进。核实项目指引真正被使用；复用原生工具完成复现、修改、针对性验证和结果呈现；把实际可下载成果与验证对应起来。

允许：受控项目指引、加载路径最小适配、一个确有必要的固定辅助、现有成果界面局部信息增强。

禁止：先建设评测中心、通用任务状态机、插件平台、全新聊天工作台、Shared 模式。不得用仅在 Codex 私有终端可运行的脚本冒充用户可用能力。

**交付**：工程师在浏览器独立完成一个真实修复并取得可复现结果。已有状态与用户未提交内容不丢失，失败提示真实。

**门槛**：V3E-A03—A08 的主要路径先成立，再扩展其他案例。

## T2 — 用第二条真实任务和保留样本检验增强

补齐选定任务集合；以相同起始输入、批准模型、运行环境和预算做成对比较。保留每一次尝试，不挑成功样本，不把维护者手工修复混进 Agent 输出。

先用另一项不同缺陷检验第一项改动，再完成保留案例。发现只是单例硬编码就撤回。对照脚本和报表采用简单文件即可，不建立评测服务。

必要时提取已出现的稳定共性；不能为了消除重复而加入新的接口家族。若保留样本参与修改，它就不再是保留样本，需更换未用于调试的样本并记录。

**交付**：成对结果、人工介入分类、费用／请求与等待分解、问题修复证据、适用范围及失败案例。

**门槛**：满足预先记录的主目标与成本保护；无收益则不发布增强。

## T3 — 受控发布、影响回归和用户签收

生成固定候选；在隔离开发部署完成实际使用、下载后重建、停止重进、容量／权限影响回归、制品回退及再部署检查。不得恢复退役服务器或自动进行生产发布。

在既有成果面板中呈现准确状态；实际用户完成新任务或自然的后续修改，并确认结果对其工作有用。既有两个身份的隔离继续回归，不要求收集一批新员工密码。

**交付**：可安装候选、变更说明、简短用户说明、有效实验记录、回退方法、签收原文及范围。

**结束**：满足 [ACCEPTANCE](ACCEPTANCE.md) 后标记 `DELIVERED`。缺少用户签收时最多 `READY_FOR_USER_ACCEPTANCE`，不让脚本替用户接受。不得自动开启下一版。

## 每次结束时的汇报

更新 [STATUS](STATUS.md)：新增能做什么、仍不能做什么、证据路径、当前唯一主要阻塞、下一步只处理什么。新想法放入候选，不变成当前任务。
