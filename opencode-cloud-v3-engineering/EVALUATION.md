# 任务对照：用真实效果决定是否保留增强

这是简单实验约定，不是要求开发评测平台。使用模板和少量文件即可。

## 1. 任务集合

建议 6 个真实任务：4 个定位／改善，2 个保留验证；允许事先确定 5—8 个。T0 先选 1 个真实任务后立即推进 T1，余下在 T2 补齐。选择、范围、数量和变更需留记录。

案例必须来自获授权的真实项目问题、用户反馈或可核实历史缺陷。人工合成案例可以做安全／状态回归，必须标为 synthetic，不能替代真实任务或计入业务成功率。

至少包含不同原因或路径的缺陷，不用改名复制同一个演示。隐藏标准答案不放进 Agent 可读工作区。保留样本的题面可交给 Agent执行，但标准答案／独立预期由评审者保管，不用于调整提示词。

若开发 Codex 已读到某样本答案或据其调参，就不能声称它严格保留；改标为开发样本，并补一个未用于调整的样本。无法严格隔离时如实说明，只做有限案例比较，不宣传泛化或统计显著。

## 2. 新旧条件必须相同

- v2 已验收基线与 v3 候选分别启动，记录源码／制品／配置／项目指引摘要。
- 同一个案例从同一提交和已记录未提交内容快照开始；各轮使用独立副本与会话，不沿用修复后的文件。
- 相同模型、Provider 路由、参数、任务题面、工具权限、名额、网络和预算。v3 指引变化就是实验因素；v2 不得偷偷加载。
- 记录本次主要变化，避免同时换模型和内核；必须变化时拆成独立实验，不合并归因。
- 锁定每任务时长、模型请求／token预算、允许必要澄清次数和人工介入规则。不得看完结果后给候选加预算。
- 初轮每案例新旧各运行一次；主改善案例至少再成对复核一次，顺序对调。小样本只支持该集合观察，不声称普遍更强。
- 排队、冷启动、模型服务耗时与实际工作耗时分别记录。非预期外部故障标记 blocked，不静默剔除；重跑两侧按同规则，保留原记录。

模板：[CASE_RECORD](templates/CASE_RECORD.json)。没有实測不填写零值来代表成功，未知为 `null`。

## 3. 主要指标

| 指标 | 规则 |
|---|---|
| 独立完成 | 独立验收满足原需求且没有人工解题、改源码或临时修环境；正常澄清和权限确认不自动判失败，但单独计数 |
| 人工解题提示 | 人指出文件/根因/修法等本应由助手完成的指引次数 |
| 人工接手 | 人直接改目标源码、测试预期或代其修环境，分别记录；有接手不能标独立完成 |
| 验证真实性 | 命令、行为与源码版本对应；未运行、失败、未知不当作通过 |
| 成果复现 | 实际 ZIP/补丁摘要与干净副本验证，二者分别记录 |
| 成本 | 请求数、可获得的 token/费用、人工时间、等待、运行时间；没有接口不给估算值冒充实测 |
| 副作用 | 无关修改、测试削弱、越权、状态损坏、资源边界回归 |

有效业务澄清不能为了追求“零提问”而省略。用户信任是主观结果，应记录使用反馈，不用测试计数直接替代。

## 4. 预先锁定发布判据

在候选实测前，在 `evidence/comparison.json` 中写下主要目标与成本保护，并记录日期与内容摘要。

本包建议：新版本不减少同集合独立完成案例数、不引入严重回归；至少一种可核实改善成立——更多案例独立完成、同样完成数下人工解题/接手减少，或原来无法信任/复现的交付现在可核验。

改进应在主案例重复观察，并在未用于调试的真实案例中仍能有效工作。数值阈值与允许成本由 T0 根据实际基线锁定，本包不预设“90% 成功率”或臆造提升幅度。不得仅以措辞更自信或测试总数变多作为主目标。

所有成本、失败、未完成与条件差异都要报告。零基础分母不能计算提升百分比。

## 5. 没有收益怎么办

基线已经足够好：交付事实与已核实的使用约定，记录 `NO_CHANGE_RECOMMENDED`；不为了 v3 名字强改内核。

一个候选失败：保留记录、撤回候选；同一假设反复失败要换假设或停止，不能不断增加 Agent/工具掩盖。

要改预算、任务范围或主目标：先更新决定记录再新开比较，不把旧结果与新结果当作同一试验。

## 6. 实施者和受测者分离

Codex 负责 WorkBench 改动、测试脚手架和结果采集。受测代码任务由运行在 WorkBench 中的原生 OpenCode完成。独立行为验收在受保护标准下执行，检查者不能同时修改标准让结果通过。

保持少量人工核对。脚本能证明文件完整和某断言通过，不能替人确认价值、风险可接受和最终签收。
