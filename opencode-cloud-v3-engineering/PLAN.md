# v3 实施方案：真实项目修复的质量增强

## 1. 交付目标

> 工程师提供正常的问题描述和必要业务信息后，能在现有 WorkBench 内获得针对原问题的修复、验证与可复现成果，减少维护者反复指导和直接接手。

主线：**问题描述 → 项目理解 → 复现与定位 → 最小必要修改 → 问题验证／相关回归 → 可检查交付 → 原地继续**。

这是一条产品验收路径，不是要硬编码七阶段工作流。OpenCode 自己组织推理与工具调用，允许必要追问、失败反馈和预算内修正；平台不建立第二套执行循环。

## 2. 当前范围

只用一个已获授权、现有运行模板可处理的真实项目。优先 Node／Vite／React 的已有项目缺陷，覆盖逻辑错误、跨文件行为和需要时的页面交互。不要为了案例强行扩大到新的语言、网络或专有软件。

选取 5—8 个真实任务作为小型对照集合，建议 6 个（4 个用于定位改善、2 个保留验证）。**T0 先准备第一个真实任务即可进入 T1，不能先建设评测平台或等待填满案例库才产生用户结果。**其余案例在改善切片可用后补齐；缺少数量不能用虚构缺陷填补。范围变更要显式记录。

项目由已有管理员准备流程接入，不新增项目列表、自助仓库导入或多人共享工作副本。用户仍用自然语言工作，不需要每次填写本包的实验模板。

## 3. 必须改变的体验，而非必做模块

### 3.1 理解项目更省人工

让工程师少重复解释目录、入口、安装命令、测试方式和行为约定。优先将已核实的简短项目指引放进现有受控指令加载路径；长资料按需读取。

指引不能包含任务答案、隐藏测试或个人密钥。普通源码内的说明可以作为任务资料，但不能改变平台授权；不要为了加载 AGENTS/Skill，打开任意项目配置和插件发现。

### 3.2 修复前后有针对问题的证据

先复现或准确说明为何无法复现，再完成修改。需要测试时，检查测试是否真正覆盖用户要求，而不是只运行一个永远成功的命令。

复用原生 Shell、测试、浏览器与现有结果面板。只有基线暴露重复工具使用错误时，才增加一个受控、局部辅助脚本；不能把工具数量当成目标。

### 3.3 工程师能判断可交付程度

在现有变更／成果界面中可回答：改了什么、哪个用户行为已验证、哪些没有验证、测试对应哪个源码版本、下载的成果是否就是被验证的内容。

原有面板已满足的内容不重写。报告和状态只是原生事实与受控验证记录的展示，不能成为新的任务真相或自动调度依据。

## 4. 推荐默认实现

保持现有结构：

```text
WorkBench 现有入口、授权与空间
        ↓
v2 的单用户完整 OpenCode（按需运行）
        ├─ 最小且已核实的项目指引
        ├─ 原生文件、Shell、测试、预览能力
        └─ 必要时一个局部验证辅助
        ↓
现有成果面板：需求关联、事实状态、版本和下载证据
```

默认新增物应很少：一份项目指引、必要的加载适配、现有验证／成果展示的局部增量、真实任务对照材料。没有复现到内核缺陷就不改内核；不为可替换性增加 Runtime 抽象。

实现细节见 [IMPLEMENTATION](IMPLEMENTATION.md)，评估见 [EVALUATION](EVALUATION.md)。

## 5. 增强决策顺序

| 基线观察 | 首选动作 |
|---|---|
| 不知道正确入口、命令和规范 | 补少量有来源的项目资料与可验证加载 |
| 工具结果未读懂、漏掉行为验证 | 修正指引或输出整理；确有重复才加小脚本 |
| 页面显示成功却没有对应证据 | 改为事实驱动的展示，区分命令和需求结果 |
| 普通环境依赖缺失 | 在同一受控模板内修正；新旧对照同等提供依赖 |
| 长会话丢约束 | 先定位资料加载／压缩问题，不先造长期记忆 |
| 原生代码有可重复缺陷 | 原生回归 + 最小补丁 + 影响说明；改变内核边界需显式决定 |
| 模型或上游服务不可用 | 报告真实阻塞；不要用代理重试、切模型掩盖 |

一次比较只改变一类主要因素。可比较多个候选，但保留一个主要实验变量，避免同时换模型、提示、工具、内核后无法归因。

## 6. 范围和风险上限

不新增共享受限 Agent、业务 Skill 迁移、多机、存储重构、自动推送/PR、生产发布工具、多 Agent 评审团、向量库、长期记忆平台、任意配置 UI。

保留原生已批准的能力，不以“质量更安全”为由裁掉完整 coding。除非现有功能直接阻止本条闭环，不开展 UI 大改、认证改造、模型服务升级或性能平台建设。

所有执行继续受 v2 运行名额、模型限流、配额、网络和停止边界控制。验证与预览不能绕开名额另开永不停止的执行集群。

## 7. 完成定义

用户在已有工作台完成真实修复，查看需求相关证据，下载对应版本的可复现成果，安全停止再继续；对照集合显示明确、可解释的质量或人工投入收益，且不以重大资源、正确性或功能退化换取。

初始不宣称任何成功率目标已经可达。先锁定指标和预算，再看数据。没有收益时允许结论 `NO_CHANGE_RECOMMENDED`：保留 v2，交付诊断而不强行发布增强版本；这不是“v3 增强已交付”。

用户签收、真实证据和回退齐备后结束，不自动进入下一版。
