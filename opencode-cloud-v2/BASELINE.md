# 基线与版本口径

## 1. 用户确认优先于过期状态文档

- 用户已明确确认：本人企业内网 ID 登录成功，整套部署和完整验收已运行；之后又确认 **v1 已完成**。
- 本开发包继承 `v0 = USER_CONFIRMED_ACCEPTED`、`v1 = USER_CONFIRMED_ACCEPTED`。
- 用户确认属于用户提供的事实，不伪造为本次生成包时重新运行了产品测试。
- 不因历史 README/STATUS 中的 `NOT_RUN`、待登录或待签收文字，重新要求用户证明旧版本完成。
- 只对 v2 修改直接影响的行为做回归；发现新缺陷则按实际证据记录，不倒推否定整个历史验收。

## 2. 版本编号与部署名称不同

| 名称 | 本包解释 |
|---|---|
| 开发包 v0、v1 | 已完成基线 |
| 开发包 v2 | 本次单机按需工作空间增量 |
| 既有 `WorkBench-v1` / `workbench-v1` / `compose.v1.json` / `v1-deploy.py` | 历史部署资源及代码名称，不因新版本编号批量改名 |
| `opencode-cloud-v0/`、`opencode-cloud-v1/` | 历史方案或记录；不重新执行里面的任务清单 |

v2 证据使用独立目录，例如本包 `evidence/` 或仓库 `opencode-cloud/evidence/v2/`。不覆盖 `evidence/v1-*`，不初始化已有原生数据库、工作文件和配额计数。

## 3. 参考代码，不是强制回退点

本次通过 GitHub 连接器读取 `main`，参考提交为：

```text

commit: 4643999fc02192116d94aa28d4489c63deec8bc6
commit timestamp: 2026-09-18T05:43:35Z
package reference check date: 2026-09-19
```

原有产品记录使用 OpenCode `1.18.31`。Codex 必须先记录实际开发 HEAD、未提交改动、制品摘要和有效部署配置。若本机更新，不得 reset/checkout 旧提交来迎合本包；只调整受影响路径说明，不扩大范围。

## 4. 远程试用已退役，与版本已完成不矛盾

参考提交的 `opencode-cloud-v0/STATUS.md` 记录：远程试用停止清理、完成私人冷备，后续默认在开发机继续工作 [S2，见 SOURCES]。

因此：

- 本包不授权恢复旧远程服务器，不自动访问旧内网地址执行写操作。
- “在开发机验证”指以开发机作为测试宿主，运行云端产品的隔离环境；不是向最终用户引入本地连接器。
- 最终部署目标需要真实、明确的授权。没有授权时可完成代码、开发环境真实运行及制品，状态为待部署/验收，不伪造线上交付。
- 原冷备可能包含凭据和私钥，只读取批准范围内的必要元数据；不得把冷备、密码、私钥或生产 Cookie 放入 Git、证据或本开发包。

## 5. 仅继承已确认的需求

单用户单独立 OpenCode 实例；纯云端产品；平台统一配置；无用户插件/MCP/模型地址/镜像编辑；模块化单体；纵向 Slice；不要复制 Agent 内核。

附带的架构材料仅借用“先可用、纵向闭环、限制修改范围”的原则，不沿用其多 Runtime、Run 领域、Code/Work/Research 三阶段及一切可替换的预设 [S0]。

本包对生命周期、容量、测试接口的描述是 **v2 设计约定**，不是声称这些能力已存在于仓库。
